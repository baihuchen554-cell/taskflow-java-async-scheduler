# 项目介绍与面试准备

下面的表述描述的是这个仓库实现的能力。建议先亲自运行、阅读关键代码并完成一个小改动，再把它写进简历；面试时按自己能解释的范围展开。

## 简历可用版本

**TaskFlow · Java 异步任务调度系统**  
技术栈：Java、Spring Boot、JDBC、MySQL、HTML/CSS/JavaScript。

- 实现任务提交、延迟执行、状态查询、失败自动重试与执行前取消，提供中文管理页面和 HTTP 接口。
- 使用 MySQL 持久化任务和执行记录，通过定时扫描、条件更新和有并发上限的线程池完成异步调度，并支持应用重启后的中断任务恢复。
- 将任务状态和执行记录纳入事务管理，保留每次尝试的结果；编写接口集成测试与持久化逻辑测试，覆盖重试预算、并发领取、恢复与状态限制。

不要添加未经测试的“百万任务”“高并发”“零丢失”“恰好一次”或“分布式集群”等描述。当前项目的定位是单实例学习项目。

## 30 秒介绍

> 我主要使用 Python，这个项目是我用 Java 补充后端工程实践的个人项目。它让用户提交任务后立即拿到编号，后台线程池执行任务，MySQL 保存任务状态和每次执行记录。我实现了延迟执行、自动重试、取消和重启恢复，并做了一个能直接操作的管理页面。重点是弄清楚请求线程、调度线程、工作线程以及数据库状态之间如何协作。

## 两分钟演示路线

1. 提交文本统计任务：展示接口先返回编号，随后得到结果。
2. 提交前一次故意失败的演示任务：展示失败记录、重试等待和最终成功。
3. 提交未来执行任务并取消：展示状态限制。
4. 打开详情或刷新页面：说明任务状态和执行记录来自 MySQL。

如果演示重启恢复，要提前准备一个正在执行的演示任务，并说明恢复后的执行可能重复，避免把重启恢复讲成“任何情况下只执行一次”。

## 常见追问

**为什么用异步？**  
耗时工作不必占着 HTTP 请求等待。接口返回任务编号后，用户可以查询进度。异步改善请求响应方式，不代表任务自身耗时一定变短。

**为什么不只给方法加 `@Async`？**  
`@Async` 解决方法交给线程执行的问题，不负责持久化任务、失败次数、计划执行时间和进程退出后的恢复。我先把任务存入数据库，再让扫描器领取。

**怎么避免同一个任务被重复领取？**  
领取时通过带状态和到期条件的 SQL 更新判定，只有更新成功的调用才执行。这个机制处理领取竞争，但不等于保证所有外部副作用只发生一次。

**线程池满了怎么办？**  
应用有明确的并发上限，没有领取的任务继续留在数据库。线程池拒绝任务的异常路径也需要释放领取状态，让后续扫描能够继续处理。

**重试两次是什么意思？**  
初次执行失败后最多再尝试两次，一轮最多三次。每次尝试都会记录，重试时间由数据库字段表示；等待时不占用工作线程一直睡眠。

**应用突然退出会怎样？**  
待执行任务仍在数据库。应用重新启动时会处理遗留的运行中任务并安排再次执行。因为退出前任务可能已经完成部分外部动作，真实业务还需要幂等键。

**为什么不能取消正在执行的任务？**  
修改数据库状态不保证 Java 方法立即停止，更不能撤销已经发生的外部操作。当前只允许取消尚未领取的任务，行为更明确。

**这算分布式调度吗？**  
不算。当前设计是单实例。多实例需要任务租约、心跳、实例归属和过期回收等机制，否则一个实例启动时可能误判其他实例正在执行的任务。

**如果继续改进，你会做什么？**  
先根据实际任务补充幂等性和超时策略，再增加重试退避、鉴权及运行监控。有真实规模需求后再考虑消息队列或分布式调度，避免为了堆技术增加复杂度。
